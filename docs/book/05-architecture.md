# Глава 5. Архитектура проекта

> **Что мы уже знаем:** мы разобрались с языком (глава 2), с тем, как Spring
> создаёт объекты (глава 3), и с тем, как объекты превращаются в таблицы
> (глава 4). Теперь собираем всё вместе: из чего состоит проект, кто за что
> отвечает и что происходит между кликом мыши и ответом сервера.

## 5.1. Главный принцип: разделение по слоям

Представьте ресторан. Гость не заходит на кухню — он говорит официанту.
Официант не готовит — он относит заказ. Повар не общается с гостем — он
готовит по заказу.

Каждая роль занимает **своё место** и общается с соседями по **чётким правилам**.
Это и есть слоистая архитектура. В нашем проекде роли такие:

| Слой | Пакет | Кто там | За что отвечает | Чего **не** делает |
|------|-------|---------|------------------|--------------------|
| **Представление** (фронтенд) | `static/` | HTML, CSS, JS | Показать данные, отправить форму | Не хранит состояние, не решает, можно ли продавать товар |
| **Веб-слой** | `controller` | `ApiController`, `ShopController`, `AdminController` | Разобрать HTTP-запрос, вызвать сервис, сформировать ответ | Не содержит бизнес-правил |
| **Бизнес-логика** | `service` | `CartService`, `OrderService`, `CatalogService`, `AuthService` | Правила магазина: остатки, статусы, суммы, роли | Не знает про HTTP |
| **Доступ к данным** | `repository` | `ProductRepo`, `CategoryRepo`, `UserRepo`, `OrderRepo` | Запросы к базе | Не принимает решений |
| **Данные** | `model` | `Product`, `Order`, … | Структура данных | Не содержит логики |
| **Ошибки** | `exception` | `ApiException`, `ErrorHandler` | Единый язык ошибок | — |

### Как выглядит «слоёный пирог» сверху вниз

```
        ┌─────────────────────────────────────────┐
        │  Браузер: HTML + CSS + JavaScript        │  ← что видит человек
        └───────────────────┬─────────────────────┘
                            │ HTTP
        ┌───────────────────▼─────────────────────┐
        │  controller  — маршруты, разбор запроса   │  ← «куда обратиться»
        └───────────────────┬─────────────────────┘
        ┌───────────────────▼─────────────────────┐
        │  service     — правила магазина          │  ← «что можно и нельзя»
        └───────────────────┬─────────────────────┘
        ┌───────────────────▼─────────────────────┐
        │  repository  — запросы к базе            │  ← «где взять»
        └───────────────────┬─────────────────────┘
        ┌───────────────────▼─────────────────────┐
        │  PostgreSQL (таблицы)                    │  ← «где хранится»
        └─────────────────────────────────────────┘
```

**Правило зависимостей (идеальное):** верхний слой может знать о нижнем,
нижний — никогда о верхнем. Сервис не знает, что существуют HTTP-запросы.
Репозиторий не знает, что существует корзина.

Почему это важно? Главная причина — **тестируемость**. Тест сервиса не
поднимает веб-сервер и не подключается к базе. Если бы правила жили в
контроллере, тестировать их пришлось бы через HTTP — медленно и неудобно.

## 5.3. Путешествие запроса: «В корзину»

Давайте проследим **самый типичный** сценарий — покупатель нажал «В корзину».
Мы пройдём по всем слоям и увидим, где именно происходит каждая проверка.

### Шаг 0. Клик

```html
<form method="post" action="/cart/add">
    <input type="hidden" name="productId" value="7">
    <button class="btn">В корзину</button>
</form>
```

Браузер отправляет HTTP POST на `/cart/add` с телом `productId=7`.

### Шаг 1. Tomcat и DispatcherServlet

Встроенный веб-сервер Tomcat принимает соединение. Spring MVC находит, какой
метод помечен `@PostMapping("/cart/add")`. Это `ShopController.addToCart`.

### Шаг 2. Контроллер — разбор запроса

```java
@PostMapping("/cart/add")
public String addToCart(@RequestParam Long productId, @RequestParam(defaultValue = "1") int qty,
                        HttpSession session, RedirectAttributes redirect) {
    return result(redirect, "/cart.html", "Товар добавлен в корзину",
            () -> cart.add(session, productId, qty));
}
```

Что здесь происходит:

* `productId` и `qty` — Spring **сам** достаёт их из тела запроса и превращает
  в числа. Если `productId` не число — Spring вернёт 400 сам, ещё до входа в
  метод.
* `session` — сессия этого посетителя (создаётся при первом обращении).
* `redirect` — «сумка» для параметров редиректа.
* `cart.add(...)` — собственно действие. Заметим: контроллер **не проверяет**
  остатки и **не считает** суммы. Он только передаёт вызов сервису.
* `result(...)` — вспомогательный метод из `FormController`: выполняет действие,
  ловит `ApiException` и формирует редирект.

### Шаг 3. Сервис — правила

```java
public void add(HttpSession session, Long productId, int qty) {
    check(productId != null && qty > 0, "Некорректное количество");
    Product product = findVisible(productId);
    Map<Long, Integer> cart = raw(session);
    int wanted = cart.getOrDefault(productId, 0) + qty;
    checkStock(product, wanted);
    cart.put(productId, wanted);
}
```

Здесь **вся** логика:

1. `check(...)` — количество должно быть положительным → иначе 400.
2. `findVisible(productId)` — товар должен существовать **и** быть видимым →
   иначе 404.
3. `cart.getOrDefault(productId, 0) + qty` — считаем, сколько уже есть.
4. `checkStock(product, wanted)` — хватает ли остатка → иначе 409.
5. `cart.put(...)` — записываем в сессию.

Обратите внимание: **в сессии лежат только id и количество**. Ни названия, ни
цен. Цены берутся из базы при отображении — так они всегда актуальные.

### Шаг 4. Репозиторий — данные

Внутри `findVisible` происходит:

```java
return products.findById(id).filter(p -> p.visible)
        .orElseThrow(() -> ApiException.notFound(ApiException.PRODUCT_NOT_FOUND));
```

`products.findById(id)` — вызов Spring Data. Дальше Hibernate формирует SQL:

```sql
SELECT * FROM products WHERE id = 7;
```

и получает строку, из которой собирает объект `Product`.

### Шаг 5. Возврат

* **Успех**: сервис вернулся без исключения → `result` добавляет
  `?msg=Товар добавлен в корзину` → контроллер возвращает
  `"redirect:/cart.html"` → Spring отдаёт браузеру код 303 и адрес
  `/cart.html?msg=Товар добавлен в корзину`.
* **Ошибка**: сервис бросил `ApiException` → `result` ловит его → добавляет
  `?error=Недостаточно на складе: доступно 3 шт.` → редирект на
  `/cart.html?error=...`.

### Шаг 6. Браузер

Браузер получил 303 → **сам** запрашивает `/cart.html?msg=...`. Сервер отдаёт
HTML-страницу корзины. JavaScript страницы:

1. в `layout.js` читает `?msg=` и показывает всплывающее сообщение;
2. убирает параметр из адреса (`history.replaceState`), чтобы при обновлении
   страницы сообщение не появлялось снова;
3. в `pages.js` запрашивает `/api/cart` и рисует таблицу позиций.

### Итоговая схема одного действия

```
Клик «В корзину»
      │
      ▼
POST /cart/add  productId=7
      │
      ▼
[ShopController.addToCart]  ← разбирает запрос, ничего не решает
      │
      ▼
[CartService.add]           ← проверяет количество, товар, остаток; пишет в сессию
      │                            │
      │                            └──► [ProductRepo.findById] ──► SQL ──► PostgreSQL
      ▼
редирект 303 → /cart.html?msg=...
      │
      ▼
GET /cart.html  →  HTML + JS
      │
      ▼
GET /api/cart → [ApiController.cart] → [CartService.viewAndNormalize] → JSON
      │
      ▼
Браузер рисует таблицу корзины
```

## 5.4. Почему корзина — в сессии, а не в браузере

Корзина лежит в `HttpSession` — на сервере. Это решение имеет последствия,
которые стоит понимать.

**Плюсы:**

* Клиент не может подделать цену: сервер всё считает сам.
* Остатки проверяются по свежим данным из базы.
* Корзина переживает перезагрузку страницы и даже закрытие вкладки (в
  пределах времени жизни сессии).

**Минусы (и как с ними живут):**

* Нужно хранить сессии на сервере (в нашем случае — в памяти, поэтому при
  перезапуске приложения корзины пропадают; в продакшене ставят Redis или
  Spring Session).
* Гостю тоже нужна сессия — она создаётся автоматически при первом
  обращении.

Альтернатива — `localStorage` в браузере. Тогда корзина пережила бы перезапуск
сервера, но: (1) её можно подделать в DevTools; (2) пришлось бы реализовывать
слияние гостевой и пользовательской корзины при входе. Для учебного проекта
серверная сессия — проще и безопаснее.

## 5.5. Где какие проверки живут (и почему именно там)

| Проверка | Где живёт | Почему |
|----------|-----------|--------|
| «Количество больше нуля» | `CartService.add` | это правило магазина |
| «Товар не хватает остатка» | `CartService.checkStock` | правило магазина |
| «Товар существует и видим» | `CartService.findVisible` | правило магазина |
| «Цена не отрицательная» | `CatalogService.saveProduct` | правило магазина |
| «Переход статуса допустим» | `OrderService.changeStatus` + `OrderStatus.canGo` | правило магазина |
| «Пользователь — админ» | `AuthService.admin` | правило доступа |
| «Пользователь вошёл» | `AuthService.require` | правило доступа |
| «Пароли совпадают» | `ShopController.register` | это про *форму*, а не про бизнес-правило |
| «Заказ принадлежит мне» | `OrderRepo.findByIdAndUserId` | правило доступа к данным |

Последние две строки интересны: «пароли совпадают» — это проверка *ввода* в
форме регистрации, а не правило магазина, поэтому она живёт в контроллере.
А вот «заказ принадлежит мне» — это уже правило доступа, и оно выражено
**самим запросом** в репозитории.

**Вывод:** если правило может быть сформулировано как «бизнес-правило
магазина», оно должно жить в сервисе. Тогда его можно покрыть модульным
тестом без HTTP и без базы.

## 5.6. Обработка ошибок — единая точка

Ошибки в проекте бывают двух видов:

1. **Ожидаемые** (бизнес-ошибки): «нет товара», «не хватает остатка»,
   «недопустимый переход статуса». Это **не** сбои программы — это часть
   нормальной работы. Они представлены типом `ApiException` с HTTP-кодом.
2. **Непредвиденные** (баги): `NullPointerException`, ошибка в коде. Их
   показывать пользователю нельзя — значит, нужен общий обработчик.

Обработка распределена так:

| Место | Что ловит | Как отвечает |
|-------|-----------|--------------|
| `FormController.result(...)` | `ApiException` из действий форм | редирект с `?error=...` |
| `ShopController.checkout` | `ApiException` при оформлении | редирект с `?error=...` |
| `ErrorHandler` | всё, что не поймали выше | JSON для `/api/...`, редирект для форм |

`ErrorHandler` — это «последний рубеж». Он смотрит на адрес запроса:

```java
if (request.getRequestURI().startsWith("/api/")) {
    return ResponseEntity.status(e.status).body(Map.of("message", message(e)));
}
String page = "/404.html";
if (e.status == 401) page = "/login.html";
if (e.status == 403) page = "/403.html";
return ResponseEntity.status(HttpStatus.SEE_OTHER)
        .header("Location", page + "?error=" + encode(message(e)))
        .build();
```

То есть **форма** получает красивую страницу с сообщением, а **JSON-API** —
честный JSON с кодом. Фронтенд при этом не различает «страницу» и «API»:
он просто запрашивает `/api/...` и получает либо 200 с данными, либо 401 с
объяснением.

## 5.7. Правило «одна ответственность» на практике

Посмотрим на `AdminController.saveProduct` — он длинный, но в нём **нет ни
одной бизнес-правила**:

```java
@PostMapping("/admin/products/save")
public String saveProduct(...) {
    auth.admin(session);                          // 1. проверка прав
    CatalogService.ProductData data = new CatalogService.ProductData(
            name, categoryId, price, description, imageUrl, stock, visible != null);
    try {
        catalog.saveProduct(id, data);            // 2. вся логика — в сервисе
    } catch (ApiException e) {
        redirect.addAttribute("error", e.getMessage());
        if (id != null) redirect.addAttribute("id", id);
        redirect.addAttribute("name", name);
        ...                                        // 3. вернуть введённое в форму
        return "redirect:/admin/product-form.html";
    }
    redirect.addAttribute("msg", "Товар сохранён");
    return "redirect:/admin/products.html";
}
```

Контроллер делает ровно три вещи: проверяет права, собирает данные из формы
в объект, перенаправляет браузер. Всё остальное — в сервисе. Именно поэтому
тесты `AdminControllerTest` проверяют маршруты и редиректы, а правила
проверяются в `CatalogServiceTest`.

## 5.8. Главное из главы

1. Проект разделён на слои: контроллеры → сервисы → репозитории → база.
   Верхний слой знает о нижнем, нижний — нет.
2. Слои нужны не «для красоты», а ради тестируемости: правила живут в
   сервисах, а их можно проверять без HTTP и без базы.
3. Любой запрос проходит один и тот же маршрут: контроллер → сервис →
   репозиторий → база → обратно.
4. Бизнес-правила живут в сервисах; проверки «ввода» могут жить в
   контроллере.
5. Ошибки — часть нормальной работы: `ApiException` + `ErrorHandler`.
6. Корзина в сессии: цены считает сервер, клиент не может их подделать.
