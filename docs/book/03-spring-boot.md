# Глава 3. Как работает Spring Boot

> **Что мы уже знаем:** мы умеем читать аннотации и понимаем, что такое
> клиент, сервер, HTTP, сессия, `BigDecimal`, `record`, `Optional` (глава 2).
> Теперь разберёмся с «магией», благодаря которой в проекте нет ни одной
> строчки, где создаются сервисы и репозитории.

---

## 3.1. Что такое фреймворк и зачем он нужен

Представьте, что вы пишете программу «скучную»: создаёте соединение с базой,
пишете SQL, разбираете ответы HTTP, читаете параметры из запроса, сами
управляете памятью. Для одного экрана — страницы каталога — это сотни строк
однотипного кода. А проект у нас на двести с лишним классов.

**Фреймворк** — это готовый «каркас», который берёт на себя всю однотипную
работу, а от вас требует только сказать «что именно делать».

Spring Boot — фреймворк для Java, который состоит из:

* **Spring Framework** — ядро: контейнер объектов, веб-слой, доступ к данным;
* **Spring Boot** — «обёртка», которая умеет настроить всё это автоматически,
  собрать приложение в один исполняемый файл и запустить его одной командой.

Главная идея Spring: **вы описываете структуру, а он создаёт объекты и связывает
их между собой**.

## 3.2. Точка входа и «старт двигателя»

```java
@SpringBootApplication
public class FlowerStoreApplication {
    public static void main(String[] args) {
        SpringApplication.run(FlowerStoreApplication.class, args);
    }

    @Bean
    BCryptPasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}
```

Разберём по строчкам.

### `public static void main(String[] args)`

Это **точка входа**. Java требует, чтобы у класса был метод `main` с такой
подписью — с неё начинается выполнение программы. Пока мы учимся, считайте,
что это «нажмите кнопку “Пуск”».

`String[] args` — параметры командной строки. Spring Boot читает из них
настройки вроде `--server.port=9090`.

### `SpringApplication.run(...)`

Вот здесь происходит «старт двигателя»:

1. Spring сканирует пакет `shop` (тот, где лежит `FlowerStoreApplication`) и
   находит все классы с аннотациями `@Component`, `@Service`, `@Repository`,
   `@RestController`, `@Controller`.
2. Создаёт **экземпляр** каждого из них.
3. Разбирает их конструкторы: понимает, что `CartService` требует
   `ProductRepo`, а `ProductRepo` — это «доступ к данным», который надо
   настроить на PostgreSQL.
4. Создаёт и связывает всё это в **контейнер**.
5. Поднимает встроенный веб-сервер (Tomcat) на порту 8080.
6. Выполняет «раннеры» — например, `SeedData` (глава 1.5).

### `@SpringBootApplication`

Три аннотации в одной:

* `@Configuration` — «это класс конфигурации»;
* `@EnableAutoConfiguration` — «настрой стандартные вещи сам: веб-сервер,
  подключение к базе, сериализацию JSON»;
* `@ComponentScan` — «найди мои компоненты в этом пакете и создай их».

**Важно:** Spring ищет компоненты **только внутри своего пакета и вложенных**.
Поэтому все классы проекта лежат в `shop` и его подпакетах — иначе Spring их
не найдёт и приложение упадёт с ошибкой «NoSuchBeanDefinition».

### `@Bean` — «объект, который создаёт не конструктор, а метод»

```java
@Bean
BCryptPasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
```

`BCryptPasswordEncoder` — библиотечный класс из `spring-security-crypto`,
который хеширует пароли. Spring не знает, что он нужен, пока вы не скажете
ему об этом методом `@Bean`. После этого метод вызывается **один раз**, а
результат кладётся в контейнер под именем `passwordEncoder`.

Все, кому нужен кодировщик паролей, получат **один и тот же** объект:

```java
public AuthService(UserRepo users,
                   BCryptPasswordEncoder encoder,   // ← сюда Spring подставил объект из @Bean
                   @Value("${app.admin.email:admin@flower.local}") String adminEmail,
                   @Value("${app.admin.password:admin123}") String adminPassword) {
```

Два способа получить зависимость в конструктор:

* **по типу** — `BCryptPasswordEncoder encoder`: Spring сам найдёт бин этого
  типа;
* **через `@Value`** — взять значение из настроек: `@Value("${app.admin.email}")`.

### Что такое BCrypt и зачем он нужен

Пароль нельзя хранить как есть. Если база утечёт, все пароли сразу утекут
вместе с ней. Поэтому хранят **хеш** — «отпечаток», который нельзя обратить
обратно в пароль.

BCrypt — популярный алгоритм хеширования. Его особенность: он **медленный**
и «сольный» (в хеш входит случайная соль). Медленный — это специально: чтобы
перебор миллиардов паролей занимал недели, а не секунды. Соль — чтобы два
одинаковых пароля давали разные хеши.

Проверка пароля делается так:

```java
encoder.matches("admin123", user.passwordHash)
```

То есть не «сравниваем строки», а «считаем хеш от введённого пароля с той же
солью и сравниваем результат».

## 3.3. Контейнер и внедрение зависимостей

**Контейнер** (в Spring он называется ApplicationContext) — это «склад», где
лежат созданные объекты. Каждый объект, помеченный `@Component`/`@Service`/
`@Repository`, лежит в нём под именем своего класса.

Отсюда следует важное правило: **объекты-«синглтоны»**. Spring создаёт по
одному экземпляру каждого компонента на всё приложение. Именно поэтому
сервис может спокойно хранить состояние в полях (например, кодировщик паролей)
— он всегда один и тот же.

### Как выглядит «ручной» Spring

Без фреймворка вы бы написали так:

```java
public class FlowerStoreApplication {
    public static void main(String[] args) {
        DataSource dataSource = new HikariDataSource(...);   // настроить пул соединений
        EntityManagerFactory emf = new HibernateFactory(...);
        ProductRepo products = new SpringDataProductRepo(emf);
        CategoryRepo categories = new SpringDataCategoryRepo(emf);
        AuthService auth = new AuthService(new SpringDataUserRepo(emf), new BCryptPasswordEncoder(), ...);
        CartService cart = new CartService(products);
        OrderService orders = new OrderService(ordersRepo, products);
        CatalogService catalog = new CatalogService(categories, products);
        // ... ещё 50 строк, а потом ещё надо поднять Tomcat
    }
}
```

Со Spring — **ноль строк**. Spring сам:

1. увидел `@Repository` на интерфейсе `ProductRepo`;
2. понял, что это «интерфейс доступа к данным», и сгенерировал реализацию;
3. создал репозиторий, подставив ему настроенное подключение к базе;
4. увидел конструктор `CartService(ProductRepo)` и создал `CartService`,
   подставив созданный репозиторий;
5. и так далее, пока не создал все компоненты.

**Это и есть внедрение зависимостей (Dependency Injection).** Ценность в том,
что:

* компоненты не знают друг о друге — `CartService` не создаёт `ProductRepo`,
  а просто «получает» его;
* вместо `new` всегда «получить из контейнера» — поэтому такие объекты
  **легко подменить в тестах** (глава 10): вместо настоящего репозитория мы
  даём мок, и код сервиса даже не замечает подмены.

## 3.4. Настройки: `application.properties`

```properties
server.port=8080

spring.datasource.url=${DB_URL:jdbc:postgresql://localhost:5432/flowerstore}
spring.datasource.username=${DB_USER:postgres}
spring.datasource.password=${DB_PASSWORD:123}
spring.jpa.hibernate.ddl-auto=update
spring.jpa.open-in-view=false

spring.sql.init.mode=never

app.admin.email=${ADMIN_EMAIL:admin@flower.local}
app.admin.password=${ADMIN_PASSWORD:admin123}
```

### Как читать эти строки

* `server.port=8080` — на каком порту слушать. По умолчанию Spring Boot взял
  бы 8080 и так; здесь указано явно для наглядности.
* `spring.datasource.*` — подключение к базе.
* `${DB_URL:...}` — **значение по умолчанию**. Синтаксис: `${имя переменной:значение
  по умолчанию}`. Если в системе задана переменная окружения `DB_URL`, будет
  использована она; если нет — взятётся текст после двоеточия.
  Это позволяет **не хранить пароли в файле**: на сервере задаётся переменная
  окружения, и файл остаётся безопасным.
* `spring.jpa.hibernate.ddl-auto=update` — Hibernate сам создаёт и обновляет
  таблицы под текущие классы. В тестах мы заменяем это на `create-drop`
  (глава 10).
* `spring.jpa.open-in-view=false` — важная настройка! По умолчанию Spring
  держит открытую сессию базы данных на всё время обработки HTTP-запроса.
  Это удобно, но «открытая сессия» означает, что соединение с базой
  занимается даже тогда, когда страница просто отдаёт статический файл.
  Мы закрываем её сразу, чтобы не держать соединения попусту.
* `spring.sql.init.mode=never` — приложение **не** выполняет SQL-файлы из
  `classpath:db/` автоматически. Скрипты `schema.sql` и `seed.sql` запускаются
  вручную через `psql` (глава 11).

### Настройки тестов — отдельный файл

В `src/test/resources/application.properties` лежит такой же файл, но
для тестов. Spring сначала смотрит в `src/test/resources`, и если там есть
`application.properties` — **использует его вместо** основного. Поэтому во
время тестов:

```properties
spring.datasource.url=jdbc:h2:mem:flowerstore-test;DB_CLOSE_DELAY=-1;DB_CLOSE_ON_EXIT=false;MODE=PostgreSQL
spring.datasource.driver-class-name=org.h2.Driver
spring.jpa.hibernate.ddl-auto=create-drop
```

— приложение работает на **встроенной H2** (в памяти), и настоящая база
PostgreSQL не затрагивается вообще. `MODE=PostgreSQL` заставляет H2 вести себя
как PostgreSQL, чтобы SQL-запросы, написанные для PostgreSQL, работали и на H2.

> **Вывод, который стоит запомнить:** файлы настроек — это «настройки по
> умолчанию», которые можно переопределить. Spring Boot сам подставляет
> значения по ключам, которые вы знаете (для Postgres, для порта, для JPA).

## 3.5. Веб-слой: как из адреса получается вызов метода

```java
@RestController
@RequestMapping("/api")
public class ApiController {
    @GetMapping("/products")
    public List<Product> products(@RequestParam(required = false) Long category,
                                  @RequestParam(required = false) String sort) {
        return catalog.visibleProducts(category, sort);
    }
}
```

Разбор:

* `@RestController` — «я контроллер, и мои методы возвращают **данные**, которые
  Spring превратит в JSON». (Аннотация `@Controller` — другая: там возвращают
  имя страницы или строку `redirect:...`.)
* `@RequestMapping("/api")` — «все мои адреса начинаются с `/api`».
* `@GetMapping("/products")` — «метод `GET`, путь `/api/products`».
* `@RequestParam(required = false) Long category` — «возьми параметр `category`
  из адреса; если его нет — передай `null`; приведи к типу `Long`».
* `return catalog.visibleProducts(category, sort);` — **возвращаем объект**,
  а Spring сам превратит его в JSON. Нам не нужно вручную собирать строку
  `{"id":1,...}`.

### `@Controller` и редиректы

```java
@Controller
public class ShopController {
    @PostMapping("/cart/add")
    public String addToCart(...) {
        return "redirect:/cart.html";
    }
}
```

Здесь контроллер возвращает **строку**. Если строка начинается с
`redirect:` — Spring говорит браузеру: «иди на этот адрес» (код 302). Если
строка не начинается с `redirect:` — Spring ищет файл с таким именем в
`src/main/resources/static` и отдаёт его.

Именно так работает «страшный» `?msg=...` в адресе: контроллер не может
отдать страницу с сообщением напрямую (после POST браузер всё равно
перезапросит), поэтому он **перенаправляет** на страницу с параметром, а
JavaScript на странице читает параметр и показывает всплывашку.

## 3.6. Транзакции: «всё или ничего»

```java
@Transactional
public Order create(User user, Map<Long, Integer> cart, OrderData data) {
    ...
    product.stock = product.stock - qty;   // списали остаток
    ...
    return orders.save(order);
}
```

**Транзакция** — это группа действий, которая либо выполняется целиком, либо
не выполняется вовсе.

Представьте: покупатель заказал два товара, и на втором не хватило остатка.
Без транзакции получилось бы: первый товар списан, заказ не создан, деньги
(в нашем случае — не деньги, а склад) «потеряны». С транзакцией: база
откатывает всё, как будто ничего не было.

`@Transactional` говорит Spring: «начни транзакцию перед методом, зафиксируй
после, а если метод бросил исключение — откати».

Почему нельзя просто `catch` и «проглотить» ошибку? Потому что тогда
Spring решит, что всё прошло успешно, и зафиксирует частичные изменения.
Именно поэтому в `OrderService.create` ошибки **не ловятся** внутри метода:
`ApiException` уходит вверх, транзакция откатывается, и только потом
`ErrorHandler` (глава 8) превращает ошибку в ответ.

## 3.7. «Автоматическая настройка» — что Spring делает сам

Spring Boot «угадывает» настройки по зависимостям в `pom.xml`:

| Если в pom есть | Spring Boot сам настроит |
|------------------|--------------------------|
| `spring-boot-starter-web` | встроенный Tomcat, обработку HTTP, JSON через Jackson |
| `spring-boot-starter-data-jpa` | подключение к базе, Hibernate, репозитории Spring Data |
| `postgresql` (драйвер) | пул соединений HikariCP |
| `h2` (только в тестах) | переключение тестов на встроенную базу |

Именно поэтому в `pom.xml` достаточно перечислить «стартеры», а в
`application.properties` — указать адрес базы. Никакого XML, никаких ручных
настроек Tomcat.

## 3.8. Как всё запускается: полная картина старта

```
mvn spring-boot:run
        │
        ▼
┌───────────────────────────────────────────────────────────────┐
│ 1. Читаем pom.xml → собираем class-файлы                      │
│ 2. SpringApplication.run(...)                                 │
│    ├─ сканируем пакет shop → находим 23 класса                 │
│    ├─ создаём репозитории (Spring Data) → настраиваем на базу  │
│    ├─ создаём сервисы, подставляя репозитории                  │
│    ├─ создаём контроллеры, подставляя сервисы                  │
│    ├─ создаём BCryptPasswordEncoder (@Bean)                     │
│    ├─ выполняем CommandLineRunner → SeedData (демо-данные)     │
│    └─ поднимаем Tomcat на порту 8080                           │
│ 3. Приходит запрос → Tomcat → DispatcherServlet → контроллер   │
└───────────────────────────────────────────────────────────────┘
```

**Ключевая мысль:** ни один объект проекта не создаётся «вручную». Spring
создал их все и связал. Именно поэтому в тестах мы можем сказать: «для этого
класса создай настоящий репозиторий, а для этого — подделку».

## 3.9. Главное из главы

1. Spring Boot — фреймворк: берёт на себя однотипную работу, вы пишете
   только «что делать».
2. `@SpringBootApplication` — точка входа + сканирование компонентов +
   автонастройка.
3. Контейнер Spring создаёт все компоненты сам и подставляет зависимости
   через конструкторы. Никто не пишет `new`.
4. `@Bean` — «создай этот объект один раз и положи в контейнер».
5. `@Value("${ключ:значение по умолчанию}")` — взять настройку; в настройках
   поддерживаются переменные окружения `${ENV:default}`.
6. `application.properties` в `src/test/resources` перекрывает основной — так
   тесты уезжают на H2 и не трогают рабочую PostgreSQL.
7. `@Transactional` — «всё или ничего»: при ошибке изменения откатываются.
8. `@RestController` возвращает объекты (JSON), `@Controller` — строки
   (`redirect:...` или имя страницы).

**Вопросы для самопроверки**

1. Что произойдёт, если убрать `@SpringBootApplication`?
2. Почему `spring.jpa.open-in-view=false` — полезная настройка?
3. Что будет, если в `pom.xml` убрать `spring-boot-starter-data-jpa`, а
   `@Repository`-классы оставить?
4. Зачем нужна транзакция в `OrderService.create`? Что произойдёт, если её
   убрать, а ошибка «не хватает остатка» будет возникать на втором товаре?
5. Почему пароль администратора хранится в настройках, а не в коде?
